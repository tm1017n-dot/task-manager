# 業務ポータル v10.1 引継ぎ設計書

最終更新: 2026-09-18  
対象リリース: v10.1.0 / 共有JSONスキーマ 6

## 1. 目的と対象範囲

業務ポータルは、共有ファイルサーバーを中心に数名で使う軽量な業務管理ツールです。タスク、案件、対応記録、業務・マニュアル・リンク、年度計画を扱い、個人の業務日誌だけは端末内に保存します。

外部サービス、サーバー、データベース、PowerShell、独自実行ファイル、外部通信を使わず、Microsoft Edge または Chrome 系ブラウザーで `index.html` を開いて運用します。共同利用では、全利用者が同一の共有JSONを選択します。

この文書は、別プロジェクトで保守・改善・再実装を行う担当者が、現行仕様と設計上の制約を再現できることを目的とします。

## 2. 成果物と配置

| 種別 | 内容 | 利用方法 |
|---|---|---|
| `業務ポータル_v10_1_ライト作成.vbs` | ライト版一式を展開するVBS | ダブルクリックまたは `cscript` で実行 |
| `業務ポータル_v10_1_ダーク作成.vbs` | ダーク版一式を展開するVBS | 同上 |
| `業務ポータル_v10_1_ライト・ダークVBS.zip` | 上記2本をまとめた配布用ZIP | 利用者への配布用 |
| `index.html` | 単一ファイルのアプリ本体 | `icon.ico` と同じフォルダーに置く |
| `icon.ico` | favicon、左上ロゴ、ショートカット用アイコン | `index.html` とセットで配置 |
| `サンプルデータ` | 復元用ダミー、共有ダミー、空の共有JSON | 初期確認・導入用 |
| `ドキュメント` | 導入・利用者・管理者・運用・受入確認 | 運用担当者向け |

v10.1はv10.2以降の「右側詳細パネル、一括操作、取り消し」を含まない安定版です。今後の作業の比較基準はv10.1とします。

## 3. 実行環境と前提

- Windows 10/11
- Microsoft Edge を推奨。共同利用には File System Access API が必要
- 共有フォルダーへの読み書き権限
- 数名程度、低頻度の更新を想定
- 利用者ごとにWindowsアカウントまたはブラウザープロファイルを分けることを推奨

`自分` の選択は認証ではありません。同一のWindowsアカウントまたはブラウザープロファイルを共用すると、ローカル保存の日誌を相互に閲覧できる可能性があります。

## 4. アーキテクチャ

```text
index.html
 ├─ HTML: 画面・ダイアログ・一覧
 ├─ CSS: ライトテーマ、レスポンシブ表示、固定ヘッダー
 └─ JavaScript
     ├─ IndexedDB / localStorage: 端末内状態
     ├─ File System Access API: 共有JSONの読込・保存
     ├─ 状態正規化・年度判定・検索・描画
     └─ XLSX生成・JSONバックアップ・通知

共有フォルダー
 └─ personal_work_portal_shared.json
       └─ チーム共有データと共有通知
```

外部ライブラリは使用しません。Excel出力はアプリ内の最小限のXLSX生成処理で作成します。

## 5. 状態モデルと保存境界

アプリ全体の状態は `state` に保持し、読込時は必ず `normalizeState()` を通します。未知・不足項目を安全な初期値へ補い、日付・選択値・文字列長を検証します。

| データ | 保存先 | 補足 |
|---|---|---|
| users / workCategories / works | 共有JSON | 利用者・業務の基礎マスタ |
| tasks / cases / records | 共有JSON | チームで扱う業務データ |
| manuals / links / repeatRules | 共有JSON | 共有ナレッジ・定期作業 |
| activityLog / notifications | 共有JSON | 共有活動と宛先別通知 |
| trash（journal以外） | 共有JSON | 論理削除データ |
| journalEntries | 端末内のみ | 本文、時間、個人メモを含む |
| journalのtrash | 端末内のみ | 日誌の削除済みデータ |
| settings | 端末内のみ | 年度、バックアップ履歴、表示設定 |

端末内の主保存先は IndexedDB です。利用できない場合だけ localStorage を予備保存先に使います。共有JSONを読み込む際は、現在端末の日誌と日誌のごみ箱、設定を残し、共有側のチームデータだけを取り込みます。

## 6. 主なエンティティと関係

```text
workCategories 1 ── * works
works          1 ── * tasks / cases / records / manuals / journalEntries
cases          1 ── * tasks / records / journalEntries
tasks          1 ── * records / journalEntries
users          1 ── * tasks.assigneeId / cases.assigneeId
users          1 ── * records.authorId / records.responseAssigneeId
users          1 ── * notifications.userId
```

- **大分類**: 業務を整理するための分類。タスク等には直接設定しない。
- **業務**: 恒常的な仕事のまとまり。
- **タスク**: 期限・進捗・完了を持つ具体的な作業。
- **案件**: 調整、照会、問題対応など、複数回の経過を追う個別事案。
- **対応記録**: 電話、メール、打合せなど一回ごとの共有記録。
- **業務日誌**: 個人が実施した作業と時間の記録。共有しない。

削除は原則として `trash` へ移動し、参照IDは維持します。復元時にIDが重複する場合のみ新しいIDを発行します。

## 7. 共有JSON仕様

共有JSONの必須トップレベル項目は次のとおりです。

```json
{
  "format": "personal-work-portal-shared",
  "schemaVersion": 6,
  "appVersion": "10.1.0",
  "sharedRevision": 0,
  "updatedAt": "ISO 8601",
  "users": [],
  "activityLog": [],
  "notifications": [],
  "workCategories": [],
  "works": [],
  "tasks": [],
  "cases": [],
  "records": [],
  "manuals": [],
  "links": [],
  "repeatRules": [],
  "trash": []
}
```

`journalEntries` と `settings` は共有JSONへ書き込みません。

### 通知

通知は `userId` を宛先に持つ共有データです。画面には選択中の `自分` と一致する通知だけを表示します。

```json
{
  "id": "UUID",
  "userId": "利用者ID",
  "type": "task_assigned",
  "title": "タスクの担当者になりました",
  "message": "タスク名",
  "targetType": "task",
  "targetId": "タスクID",
  "createdAt": "ISO 8601",
  "readAt": "",
  "dedupeKey": "重複防止キー"
}
```

担当割当時、期限前日、期限超過時に作成します。期限通知はアプリ起動または共有データ再読込時に重複防止キーで追加します。

## 8. 共有保存と競合検知

共有JSONはデータベースの排他制御を持ちません。保存フローは次のとおりです。

1. 端末内状態を保存する。
2. 前回読込時の `sharedRevision` と、保存直前に読み直した共有JSONの `sharedRevision` を比較する。
3. 一致すれば `sharedRevision + 1` で共有JSONを丸ごと書き込む。
4. 不一致なら書き込みを停止し、利用者へ再読込を案内する。

同一レコードを同時に編集しない運用が前提です。競合を自動マージしない理由は、ファイルサーバー方式ではレコード単位ロックや信頼できる更新順序を持たないためです。

## 9. 画面と主要処理

| 画面 | 主な役割 | 重要な処理 |
|---|---|---|
| ホーム | 自分/全体の状況確認 | KPI、期限超過、案件、日誌、共有活動 |
| タスク | 日常作業の管理 | 検索、絞込、直接編集、チェックリスト |
| 業務日誌 | 個人の作業記録 | ローカル保存、必要時のみタスク進捗を共有 |
| 案件 | 非定型事案の経過管理 | 主担当、状況、次の対応、関連タスク |
| 対応記録 | 一回ごとの経緯 | 記録者、次の対応担当、案件・タスク関連付け |
| 共同利用 | 共有JSONと利用者の管理 | 接続、再読込、利用者マスタ |
| データ管理 | バックアップと出力 | JSON復元、Excel出力、ごみ箱 |
| 年度設定 | 年度切替処理 | 複写、定期タスク生成、年度またぎ確認 |

ページ移動は `navigate()`、描画切替は `applyPage()` と `renderCurrentPage()` が担当します。ページ移動時は先頭へスクロールします。

## 10. 年度ロジック

年度は4月1日から翌年3月31日です。タスク・案件には `fiscalYear` を保持しますが、開始日・期限日が表示対象年度と重なる場合は年度またぎとして表示します。

- 年度複写: 対象タスクを翌年度へ複写し、状態とチェック状態をリセットする。
- 定期タスク: weekly / monthly ルールから該当年度分を生成し、発生キーで重複を防止する。
- 年度開始チェック: バックアップ、複写、定期タスク、年度またぎ確認の実施を支援する。

## 11. バックアップ、復元、出力

- JSONバックアップは端末内の日誌も含む全状態を保存する。
- 共有運用では、共有JSON自体も定期的に別の保存先へコピーする。
- 復元前には必ず現在の状態をバックアップする。
- 全データExcelには共有データと、現在選択中利用者の日誌を出力する。

## 12. セキュリティと運用上の限界

- 認証・権限管理・暗号化・監査証跡は提供しない。
- `自分` の選択は画面表示と日誌の所有者指定のための設定である。
- 通知本文も共有JSONに保存されるため、機微な情報を書かない。
- ブラウザーのサイトデータ削除やプロファイル初期化により、ローカル日誌が失われる可能性がある。
- 共有フォルダーのアクセス権と、OSアカウント管理は運用側で実施する。

## 13. 保守・改修の手順

1. 既存の共有JSONと対象端末のJSONバックアップを取得する。
2. `index.html` を複製し、変更前後で共有JSON仕様が変わる場合は `SCHEMA_VERSION` と正規化処理を更新する。
3. 共有項目を追加する場合は、`emptyState()`、`normalizeState()`、`sharedDataObject()`、サンプルJSON、設計書を同時に更新する。
4. 日誌に関する変更は、共有JSONへ漏れないことを確認する。
5. ライト版を基準にダーク版を再生成し、JavaScript部分が完全一致することを確認する。
6. VBSを再生成し、実行展開後のファイルハッシュとHTML構文を検証する。
7. 最低2端末で、通常保存、競合検知、再読込、日誌の非共有を確認する。

## 15. 受入確認の最小セット

1. ライト版とダーク版をEdgeで開ける。
2. タスク、案件、対応記録、日誌、マニュアル、リンクを追加・編集・削除・復元できる。
3. タスク一覧の期限・進捗・担当者を直接変更できる。
4. ホームの件数カードから該当タスクの絞込一覧へ移動できる。
5. 担当割当と期限の通知が宛先利用者に表示される。
6. 共有JSONへ接続した2端末で、先行保存時に競合を検知できる。
7. 日誌本文・所要時間・個人メモが共有JSONに含まれない。
8. JSONバックアップとExcel出力が完了する。
